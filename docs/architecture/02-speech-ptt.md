# 02 Foot PTT, audio capture, STT, parser

## 1. Foot PTT

### 1.1 Device types supported

| Type | Detection | Access |
|---|---|---|
| HID keyboard | EV_KEY, KEY_* | evdev |
| **HID mouse button** | EV_KEY, BTN_LEFT/RIGHT/MIDDLE | evdev (candidate device looks like this) |
| HID joystick / gamepad | BTN_TRIGGER, BTN_0… | evdev |
| Vendor or consumer HID | EV_KEY consumer codes, or hidraw | evdev, hidraw adapter only if needed |
| USB serial | /dev/ttyACM*, ttyUSB* (e.g. CTS line) | serial adapter only if needed |

Build order: evdev first (covers the first three); hidraw and serial only if the real pedal needs them.

### 1.2 Pedal identification (please run in a terminal)

```
sudo apt install evtest
sudo evtest /dev/input/event14      # confirm 04d8:0055 first in the device list
```
Press and hold 3 s, release; repeat five times; do five quick taps. Then unplug and confirm the device disappears from `lsusb`. Please send me the output.

Questions it answers: is this the pedal; which code; does it send **press on down and release on up** (value 1/0), or a click pulse on press only? A pulse-only pedal **cannot do hold-to-talk** and must be reconfigured or replaced. Also whether it autorepeats (value 2, ignored by design) and bounce timing.

#### Guided test (`/home/user/ptt_guide.txt`, 14:23, prompted 5 s holds)

| Button | Trials | Result |
|---|---|---|
| RIGHT | 3 | 3 x PULSE: one 1.0 ms pulse after PRESS, **nothing on release**. Presses at 4.65, 16.44, 24.32 s with no event between them, although the foot must have come up each time |
| LEFT | 3 | EDGE, NONE, PULSE, plus one pulse in the get-ready period: 4 pulses, all 1.0 ms, timing does not follow the prompts |

**Verdict: FAIL for D-01.** RIGHT release is not reported, so RT stop cannot be detected.

Conclusions:
1. **The device never reports duration.** A real tap lasts tens of milliseconds at least, so the 1 ms pulses are generated by firmware. Contact bounce is ruled out.
2. RIGHT does not report release at all (guided test), so the press/release-pair idea is rejected for RIGHT. What LEFT represents is still unclear, but it is also a 1 ms pulse.
3. Hold-to-talk with this pedal is therefore **not possible** as it stands. Replace it or fit hold-type firmware.
4. Do not read it through hidraw: it would wake the CPU about 1000 times a second. evdev only delivers changes.

| Hold test shows | Meaning | Action |
|---|---|---|
| 1 at press, 0 at release (after bounce) | Works | Debounce covers bounce; keep §1.4 |
| Short pulse at press and another at release | Edges exist but are indistinguishable | Not trusted: one lost pulse inverts TX state. Replace |
| Short pulse at press only | No release information | **Cannot do hold-to-talk.** Replace |
| hidraw shows more than evdev | Hidden signal in padding or X/Y | Evaluate a hidraw adapter |

If replacement is needed: choose a pedal documented as holding its key or button while pressed, verified with evtest before purchase in quantity; or wire the existing switch to a microcontroller with hold-type HID firmware. Latch mode (tap on, tap off) exists as an option but is not a substitute: it trains the wrong foot habit and risks a stuck transmission.

### 1.3 Binding and grab

- Match VID:PID + name + phys path + key code. `04d8:0055` is a generic Microchip demo ID and no serial was visible (empty `Uniq`), so VID:PID alone is not proof of identity.
- `EVIOCGRAB` while the app runs, so a mouse-type pedal cannot click the touch UI. Plus udev `LIBINPUT_IGNORE_DEVICE=1` so the desktop ignores it when the app is not running.
- `EVIOCSCLOCKID` = CLOCK_MONOTONIC. Handle SYN_DROPPED through libevdev resync.
- Hot-plug: libudev monitor; rebind on add; synthetic release on loss.
- "Learn pedal": listens on all candidate devices, asks for a 2 s hold, shows device, code and **measured hold time**, writes `config/ptt.json`. A press shorter than 100 ms during the hold step is refused as "pulse-type device, cannot do hold-to-talk".

Udev rule: `deploy/panel/72-atc-ptt.rules`, installed by `deploy/setup_panel.sh` (D-200). It must sort before `73-seat-late.rules`, and it never matches a keyboard.

`uaccess` grants the active local seat user read and write; no root and no group membership needed. Read-only is ensured by the app, which opens the pedal `O_RDONLY` (question A-1 of the 2026-11-24 briefs is open).

### 1.4 Timing (all configurable; defaults are starting points to tune)

| Parameter | Default | Range |
|---|---|---|
| debounce | 20 ms | 10–30 |
| min duration | 250 ms | 100–500 |
| max duration (stuck) | 30 s | 10–60 |
| pre-roll | 300 ms | 200–500 |
| release tail | 200 ms | 150–300 |
| mode | hold | hold / latch |

Debounce acts on the edge *after* the first: press is reported immediately, release is confirmed after the window, so debounce never delays keying.

### 1.5 PttInputManager

Merges pedal, on-screen button and keyboard. First source to press owns the transmission; others are ignored and logged until it releases. Pedal missing at Start: warn or block by config.

### 1.6 PTT discipline metrics

| Metric | Measured from |
|---|---|
| Spoke before keying | Speech energy in pre-roll that continues across t0 |
| Released early | Speech energy continuing through the tail |
| Key-to-speech delay | t0 to first speech |
| Empty, short, stuck, blocked, stepped-on | Transmission events |

Clipped audio is flagged and kept separate from STT errors.

## 2. Audio capture

- libpulse stream, 16 kHz S16 mono requested, small fragments, latency-adjusted. PulseAudio resamples (device was running at 44.1 kHz stereo).
- Always capturing into a 60 s ring (about 1.9 MB). Utterance cut = [t0 − preRoll, t1 + tail].
- **Timing (changed 2026-11-23):** PulseAudio's latency estimate is not used. In tests it misplaced audio by 244 ms (backlog at start) and 263 ms (late start), settling only after seconds. Instead, offset = smallest (arrival − samples/rate) over 2 s. Same three tests on a synthetic FIFO source afterwards: within 0.2 ms of truth. This excludes the headset's own converter and USB delay, which is **to be measured on the panel**; a fixed delay shortens the effective tail by that amount.
- Lost audio (server-reported hole, reopened stream, or delay lasting 2 s) is filled with silence and the cut is flagged `gap`.
- Stream is pinned to its source (DONT_MOVE): unplugging the headset reports Lost and retries each second; it never falls back to another microphone. A playback monitor as default source is refused.
- No noise suppression, AGC or echo cancellation by default; never radio effects on trainee audio.
- Readiness check: device present, not muted, level above floor. The H540 exposes mute and volume keys, so headset mute is a real failure case.
- **H540 result (user, 2026-11-23, mouse as stand-in PTT on event5, source volume 97 %):** `audio_probe` end of run: largest block delay 5.7 ms, 0 gaps (arrival delay only, not the headset's converter delay). `ptt_record`: 3 recordings, no gaps, full pre-roll. Peaks -0.9, -4.9 and 0.0 dBFS (the last clipped: rejected), so the volume is too high. The third was a 29.94 s hold, released while speech was detected; 30 s limit not reached. Not shown in the pasted output: headset mute and unplug.
- Checks per utterance: empty, peak-clipped, low SNR, speech at either cut edge.
- `IAudioSource` allows ALSA or a WAV-fed fake.

Leading candidate: **Vosk small**, because it streams. Not a decision (P-04).

Cautions:
1. Prebuilt binaries may assume AVX2. Every binary must be verified on this CPU; whisper.cpp is built without AVX2/FMA.
2. whisper pads to 30 s windows; reduced audio context is tested as an option, with accuracy reported.
3. Vosk silently ignores grammar words absent from its lexicon. `stt_bench --lexicon` lists missing words ("niner", callsigns, local names) first; those need model adaptation or spoken-form aliases.
4. Grammar always includes `[unk]`, and is restricted at word level, never to the expected sentence of the current step.

## 4. Parser

Pipeline: text → normalise (niner/tree/fife, phonetic letters, number groupings, spoken variants from `vocabulary.json`) → tag slots → intent patterns → parameters → classification.

| Class | Rule |
|---|---|
| RECOGNIZED | One intent, all required fields present, every critical field above threshold |
| PARTIAL | Intent clear, required field missing |
| AMBIGUOUS | Two intents or two critical values plausible, or critical confidence low |
| UNRECOGNIZED | No intent, empty, or unusable audio |

Rules:
- Critical values are never corrected, snapped to the nearest valid value, or filled from the expected step. "Runway two eight" when 27 is active is a *trainee instruction with runway 28*, sent to the validator.
- Field confidence = minimum word confidence in its span. Low critical confidence → pilot says "say again".
- Back-references resolve from ScenarioContext only with exactly one candidate.
- Raw text, normalised text, confidence and parse are all logged, so STT errors can be separated from trainee errors at debrief.
- Intent patterns live in JSON and are PLACEHOLDER until validated.

Illustrative only: "Eagle Four Two One, taxi via Alpha Three, hold short runway Zero Nine" →
`{"callsign":"EAGLE-421","intent":"TAXI_INSTRUCTION","taxiway":"A3","runway":"09","instruction":"HOLD_SHORT"}`
